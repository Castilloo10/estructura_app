BTal es una app nativa móvil (iOS/Android) primero; la web es un canal secundario (landing/SEO/compartir). Stack, flujos y estructura para una app multi-usuario con IA integrada.

Dónde vive el código. La app BTal es el repo btal-v2 (React Native + Expo · carpeta E:\Descargas\BTAL APP\btal-v2), que incluye también el backend (functions/) y las reglas de seguridad (firestore.rules). 1 codebase TS/React → nativo real iOS+Android (120Hz, materiales del SO) + web en DOM vía React Native Web.

5 pasos
01
Página de bienvenida
Si el dispositivo ya tiene sesión activa, Firebase Auth la detecta automáticamente y salta directo al paso 3. Sin interacción del usuario.
02
Login Firebase Auth
Email + contraseña, con segundo paso 2FA TOTP si el usuario lo tiene activado. Si la contraseña falla, opción de recuperación por email. Sesión persistente entre visitas. Google sign-in → Fase 4.5 · Apple → lanzamiento.
03
Carga de datos
La app lee Firestore /users/{uid} (session.ts carga el documento y hidrata los stores, con reintentos). El indicador de guardado muestra el estado en tiempo real.
04
Dashboard con sus datos
Ve su menú, entrenos y lista exactamente como los dejó. Los cambios se guardan automáticamente con debounce.
Acciones disponibles
Editar comidas, macros o pesos de ejercicios
Marcar días de entreno completados
Ajustes → cambiar objetivo → regenerar con IA
Actualizar peso y medidas actuales
05
Cerrar sesión
Firebase borra el token local. La siguiente visita empieza en el login. Los datos permanecen en Firestore intactos y sincronizados.
4 pasos
01
Pulsa «Probar sin cuenta» Firebase Auth
Firebase crea una sesión anónima con uid temporal. Sin email ni contraseña. Funciona igual que una cuenta real en términos técnicos, pero el documento se siembra con un campo expiresAt: la sesión de invitado caduca a los 3 días de su creación (no se renueva con el uso).
02
App con datos de demostración
Se carga la plantilla demoUser.ts: un perfil demo completo con datos de ejemplo (comidas, entrenos, compra, suplementos) — no el esqueleto vacío de defaultUser.ts. El usuario puede explorar toda la interfaz sin restricciones.
Limitaciones visibles
Banner con cuenta atrás: la sesión de prueba caduca a los 3 días
Botón siempre visible: «Crear cuenta para guardar»
No puede usar la generación con IA
03
Puede editar todo en modo prueba
Los cambios se guardan en Firestore bajo el uid anónimo y persisten hasta que la sesión caduca (expiresAt · TTL de 3 días desde la creación, no renovable).
04
Conversión a cuenta real (opcional)
Al registrarse, Firebase vincula el uid anónimo al nuevo email. Todos los datos que editó en modo demo se conservan automáticamente y la cuenta deja de caducar (se limpia expiresAt). Cero fricción.

Gemini 2.5 Flash
Modelo en producción: gemini-2.5-flash (se descartó flash-lite porque infra-dimensionaba las raciones, ~73% del objetivo kcal). La API es de pago, sin free tier: una generación completa (menú + entreno + compra) ronda ~15K tokens (≈3K de entrada + ~12K de salida) ≈ €0,025 por generación — un Pro de 9,99€ cubre ≈400 generaciones. maxOutputTokens a 65536 para que el scope «Todo» no se trunque. La API key nunca sale del servidor (secreto en Cloud Functions). Sanitizar siempre los datos del perfil antes de meterlos en el prompt para evitar prompt injection.

Pagos · IAP
RevenueCat + IAP Apple/Google
En una app nativa, Apple y Google obligan a cobrar los bienes digitales con su IAP (rechazan pasarelas de pago externas). RevenueCat es la capa que unifica StoreKit (iOS) y Play Billing (Android): defines products en App Store Connect y Play Console, los agrupas en offerings con entitlements, y el SDK react-native-purchases resuelve compras, restauración y receipts sin servidor propio. Comisión 15% (Small Business Program, <1M$/año). RevenueCat es gratis hasta 2,5K$/mes de ingresos. Su webhook firma cada evento (compra, renovación, cancelación, reembolso) → Cloud Function lo verifica e idempotente actualiza Firestore.

Optimizaciones mobile-first para minimizar costes (revisión 14-may PM)
Reorganización tras pivote mobile-first: el CDN Cloudflare baja de prioridad (la web es solo ~1% del tráfico · hosting transfer ~2 €/mes a 10K DAU). Entran 5 optimizaciones nativas que solo existen porque la app va por React Native + Expo (Firestore native, offline persistence, FCM topics, almacenamiento local nativo, EAS Update OTA).
01
BD propia de alimentos (OpenFoodFacts) + cache-first Fase 6B ✅ ⭐ alto impacto
Colección /foods/{key} sembrada del dump de OpenFoodFacts (~25K alimentos ES, ~4 MB) + sync semanal de deltas. La generación y el buscador LEEN de la BD propia (cache-first) y solo llaman a la API en vivo en cache-miss · cada hit = 0 roundtrip. 0 € a cualquier escala (ODbL gratis · sin paid tier) · cobertura fuerte de marcas blancas españolas.
02
Offline persistence + listeners selectivos por tab pre-launch ⭐ alto impacto
Habilitar persistentLocalCache en Firestore · la app funciona en gym sin cobertura. Cancelar listeners cuando la tab no está activa (el navegador de tabs nativo mantiene viva la pantalla · sin esto se consume cellular + battery innecesario). Crítico en mobile: cada read = network call = battery drain + plan de datos del usuario. Reduce reads ~40% en uso real.
03
Firestore SDK nativo en React Native nativo · Fase 4.5/5 NUEVA mobile-first
Usar @react-native-firebase/firestore (SDK nativo) en lugar del JS SDK genérico. Beneficios: menos consumo de batería (sin overhead de un WebView/bridge JS), offline persistence robusta sobre almacenamiento nativo (SQLite, no IndexedDB), background sync cuando la app no está activa, mejor rendimiento en queries grandes. Cambio transparente: el código React sigue igual tras la capa de servicios.
04
Push notifications + FCM topics (sustituye emails) nativo · Fase 4.5/5 NUEVA mobile-first
Suscribir usuarios a topics FCM (recordatorio_comida, recordatorio_entreno, news) en lugar de enviar a tokens individuales. Una llamada → millones de devices. Ahorra emails y SMTP: en vez de emails (Brevo/Mailgun paid tier), push nativo gratis ilimitado. Smart batching de horarios en Cloud Function una vez/día.
05
react-native-mmkv / AsyncStorage para flags locales nativo · Fase 4.5/5 NUEVA mobile-first
Para data no crítica (settings UI, último tab visitado, dismissed banners, preferencias display) usar storage nativo en lugar de Firestore writes. Cero coste: cada write evitado en Firestore es coste evitado. La synchronización cross-device sigue para todo lo relevante (perfil, planes, registros). Solo usar para state UI que tiene sentido sea per-device.
06
Annual Plan IAP + Family Sharing strategy Fase 7
Estrategia futura: plan anual con descuento en App Store / Play Store con auto-renew + Apple Family Sharing (1 sub Pro = compartida con hasta 5 family members · marketing "Plan familiar incluido" reduce fricción de conversión) para subir retención y ARPU. Auto-renew nativo: churn bajísimo (Apple/Google avisan al user de la renovación con su flujo nativo de gestión de suscripciones). Re-precio pendiente: hoy Pro es 9,99 €/mes sin plan anual · el precio del anual se decidirá con datos reales de conversión.
07
EAS Update · OTA bundles post 1K DAU NUEVA mobile-first
Para hotfixes y cambios solo-JS (UI, copy, bugfix), enviar el bundle JS actualizado por aire con EAS Update sin pasar por App Store review (1-7 días). Solo los cambios nativos (módulos, permisos, deps que requieren prebuild) obligan a resubmission. EAS Update está incluido en el free tier de Expo para volúmenes moderados (planes de pago a escala). ROI: cada bugfix urgente sale en horas vs semana.

Firestore composite indexes optimization ad-hoc
Cuando aparezcan slow queries en Cloud Console > Firestore > Performance, crear índices compuestos solo para las queries que se ejecutan. Eliminar índices auto-creados que no se usan (cuesta storage). firestore.indexes.json en el repo permite trackear vía CI. Independiente del canal · sigue siendo válido.
